## Что проверить нельзя без вас (НЕТ ДАННЫХ ДЛЯ НАДЁЖНОГО ВЫВОДА)

- **Ваш конкретный компьютер.** CI — это Windows Server 2025 с виртуальным кабелем. Реальные драйверы (Realtek, USB-гарнитуры, Bluetooth HFP) там не проверить. Если запись не пойдёт, нажмите «Настройки → Предполётная проверка → Скопировать диагностику» — там будет точный код ошибки Windows.
- **Значок в трее** не сделан: его нужно проверять на настоящем рабочем столе.
- **Подпись установщика** включится, когда в секреты репозитория будет добавлен сертификат.
- **Глобальная клавиша Ctrl+Alt+R**: код и маршрут проверены тестами. Сама регистрация `RegisterHotKey` в CI не проверяется: там нет интерактивного рабочего стола.

**Что показал отчёт**
- Системный модуль записи готов (`ready: true`, режимы mic/system/both). Микрофон по умолчанию — «Набор микрофонов (Intel Smart Sound)», включён, громкость 98 %.
- Все попытки записи шли через **окно браузера**, и Windows отвечала `NotReadableError` за 120 мс. В журнале ядра нет ни одной попытки через системный модуль.
- В системе работают Discord (виден в журнале доступа к микрофону) и Voicemeeter (десяток виртуальных входов).

**Причины в MONO (обе подтверждены кодом и сквозным тестом)**

| # | Причина | Исправление |
|---|---|---|
| 1 | Когда системный модуль однажды был недоступен (ошибка, исправленная во 2-м раунде), MONO **сохранял** переход на «Микрофон браузера» в настройки и больше не возвращался к модулю. Старый тест закреплял именно это поведение | Переход на браузер действует только сейчас и не сохраняется. Студия показывает источник, который реально будет записывать |
| 2 | Если браузер не открыл микрофон, лестница восстановления пробовала **тот же** браузер. Путь «браузер → системный модуль» не существовал | Разнородный путь в обе стороны: окно не открыло микрофон → системный модуль. После удачной записи модуль запоминается как источник (сохраняется после записи: во время записи ядро отвечает CAPTURE_BUSY), отметка «звук проверен» не сбрасывается |
| 3 | Сбои старта системного модуля не попадали в журнал ядра | Пишутся как `native_capture_failure` |
| 4 | При «микрофон занят» не было инструкции | Кнопка «Как освободить микрофон»: кто держит микрофон (Discord), Voicemeeter как аппаратный вход, две галочки «Монопольный режим» в свойствах микрофона [1] |

Проверено новым сквозным тестом: окно получает `NotReadableError`, MONO сам переходит на системный модуль, запись сохраняется, источник «mic» запоминается, диагностика показывает `source: mic`.

- Откроет ли **системный модуль** микрофон Intel на этом ноутбуке, пока его держит Discord или Voicemeeter. Если программа захватила микрофон в монопольном режиме, модуль получит `AUDCLNT_E_DEVICE_IN_USE`, и поможет только инструкция из п. 4.

## Раунд 4 — «Это не микрофон занят» и ошибка при выборе папки (19.11.2026)

### Микрофон: что на самом деле означает `NotReadableError`
Первоисточник — код захвата Chromium для Windows (`media/audio/win/audio_low_latency_input_win.cc`, зеркало на GitHub) [1]:
- Если драйвер заявляет поддержку RAW и не включён системный эхоподавитель, Chromium открывает микрофон с `AUDCLNT_STREAMOPTIONS_RAW`.
- Если `IAudioClient::Initialize` вернул ошибку, Chromium **не повторяет** попытку ни без RAW, ни с другим форматом.
- Отдельно Chromium различает только «нет доступа», «устройство занято» (`AUDCLNT_E_DEVICE_IN_USE`) и «устройство удалено». **Всё остальное** — одна общая ошибка, и страница получает её как `NotReadableError`.

Сторонний проект подтверждает изменение: с Chromium 152 микрофоны, поддерживающие RAW, открываются в этом режиме, и выключить это нельзя [2]. Наш модуль записи открывает микрофон в общем режиме без RAW, а при отказе повторяет попытку через конвертер Windows — тот же обходной путь, что в [2].

**Ошибка MONO:** `NotReadableError` переводился как «устройство занято / монопольный режим». Совет «закройте программы» не мог помочь.

**Исправления**
- Новый код `BROWSER_OPEN_FAILED` с честным текстом. `DEVICE_BUSY` оставлен только для настоящего `AUDCLNT_E_DEVICE_IN_USE` от модуля.
- **Проба модуля:** открыть микрофон на 0,5 с, вернуть HRESULT каждого шага, формат устройства, заявленную поддержку RAW (`PKEY_Devices_AudioDevice_RawProcessingSupported`) и принимает ли устройство 48 кГц/стерео/16 бит. Проверено в CI на настоящем Windows в двух вариантах: доступ разрешён → открыто, есть кадры и формат; доступ запрещён → `0x80070005`.
- **Глубокая диагностика** сравнивает три разных способа: окно без обработки, окно с обработкой и системный модуль. По результату выносит один вердикт: сбой только браузера, сбой драйвера (с шагами), микрофон действительно занят или доступ запрещён.
- В лестницу попыток браузера добавлена ступень с обработкой.
- Источник, ранее закреплённый за браузером, один раз переносится на модуль, и MONO сообщает об этом.

### Ошибка при выборе папки
Воспроизведено в браузере с модулем, который стартует 12 с (первый запуск однофайловой программы .NET на Windows):
- ядро обрабатывает запросы по одному, а фоновая диагностика микрофона ждала старта модуля **до 8 с**, и в это время стояли все остальные запросы окна;
- окно опрашивает состояние с тайм-аутом 3 с и показывало **«Связь с записью потеряна»**, хотя записи не было;
- онбординг после выбора папки ждал запуска модуля.

**Исправления**
- Диагностика и проба не ждут модуль, а сразу отвечают «запускается».
- Сообщение о потере связи показывается только во время записи.
- Шаг с папкой завершается сразу после настройки архива; шаг со звуком ждёт модуль терпеливо.

**Тесты:** первый запуск без модуля, с модулем, с реалистичным окном выбора (6 с и 20 с) и с медленным стартом модуля.

**НЕТ ДАННЫХ ДЛЯ НАДЁЖНОГО ВЫВОДА:** точный текст ошибки на ноутбуке пользователя неизвестен. Причина выше — воспроизведённая и устранённая гипотеза, не подтверждённая на его машине.

### Самописец ядра
Журнал записывался с задержкой 500 мс и в папку, которой при первой записи ещё не было. Поэтому записи терялись именно при падении на старте. Теперь журнал пишется сразу и сам создаёт папку.
