# MONO TRANSCRIBE 0.4.0 — One-Click Self-Hosted Desktop

**Продукт:** локальная SPA/PWA-аудиостудия, работающая в отдельном оконном окружении.
**Главное изменение 0.4:** Python supervisor, встраиваемые Node.js/FFmpeg/FFprobe,
запуск без терминала и портативный экспорт/импорт библиотеки.

## Установка

**Windows:** скачайте `MONO-Setup-<версия>.exe` (артефакт сборки «Windows installer» в GitHub Actions) и
запустите его. Это обычный мастер установки: без прав администратора, со всем необходимым внутри —
Python, Node.js, FFmpeg и модулем записи звука компьютера. После установки появится ярлык
«MONO Transcribe» на рабочем столе и в меню «Пуск». Удаление — через «Параметры → Приложения»;
записи и настройки при этом сохраняются.

## Установка из исходников в один клик

В корне проекта лежат установщики. Запустите тот, что подходит вашей системе:

| Система | Файл | Как запустить |
|---|---|---|
| Windows 10/11 | `INSTALL-MONO-Windows.cmd` | Двойной щелчок |
| macOS | `INSTALL-MONO-macOS.command` | Двойной щелчок в Finder |
| Linux | `INSTALL-MONO-Linux.sh` | «Запустить как программу» или `./INSTALL-MONO-Linux.sh` |

Установщик:

1. Проверяет Node.js 20+, Python 3.11+ и FFmpeg. Недостающее ставит сам: на Windows через `winget`,
   на macOS через Homebrew, на Linux через `apt`/`dnf` — после вашего подтверждения.
2. На Windows при наличии .NET SDK 10 собирает модуль записи звука компьютера. Без него MONO пишет
   микрофон через окно браузера.
3. Проверяет, что сервер, ядро архива и FFmpeg запускаются.
4. Создаёт ярлык **MONO Transcribe** на рабочем столе (на Windows — ещё и в меню «Пуск») и запускает
   приложение.

Ярлык запускает локальный сервер на `127.0.0.1:4173` и открывает его в отдельном окне Edge или Chrome
без вкладок и адресной строки — это не Electron. Консольных окон нет. Закрыли окно — сервер
остановился. Журнал установки: `%TEMP%\mono-install.log` (Windows) или `$TMPDIR/mono-install.log`.

Если macOS пишет, что файл нельзя открыть (архив скачан из интернета): **Системные настройки →
Конфиденциальность и безопасность → «Всё равно открыть»**. Начиная с macOS 15, обойти это через
контекстное меню нельзя. После `git clone` такой проблемы нет.

## Что получает конечный пользователь

После сборки для его ОС пользователь распаковывает архив и дважды нажимает:

- **Windows:** `MONO Transcribe.exe`
- **macOS:** `MONO Transcribe.app`

Сразу запускаются локальный backend и отдельное окно приложения.
Node.js, Python и FFmpeg устанавливать **не нужно**, если использована готовая
проверенная PyInstaller-сборка с runtime. Сервер слушает **только 127.0.0.1:4173**,
не публикуется в интернете. Окно закрывается — backend завершается; прерванные
задания восстанавливаются при следующем запуске.

Базовые действия (запись, импорт, библиотека, редактирование) не требуют облачного
аккаунта. **Для транскрибации через Groq всё равно нужен персональный API-ключ и
доступ в интернет.** Ключ не попадает в браузер: см. «Настройка Groq» ниже.

Это оконный shell поверх локально работающего PWA. Он **не выполняет скрытую
установку PWA в браузер**: установка управляется браузером. Для конечного
пользователя отдельная установка PWA не нужна.

## Что находится внутри

```
MONO Transcribe(.exe/.app)
  └── Python/PyInstaller supervisor
        ├── one-instance OS lock
        ├── persistent, isolated user/browser data
        ├── Node 22 (sidecar)
        │    ├── SPA/PWA static server on localhost:4173
        │    ├── local upload/job queue + recovery
        │    └── FFmpeg + FFprobe (sidecars)
        ├── health check bound to launched instance ID
        ├── Chromium/Edge app window or native WebView
        └── crash/close cleanup and user-visible errors
```

**Зачем фиксированный порт?** IndexedDB и Service Worker привязаны к origin
(протокол, host, порт). Изменение `4173` приводило бы к «пустой библиотеке»
даже без физической потери записей. При конфликте порта приложение сообщает
об ошибке и не начинает работу с чужим процессом.

**Почему приложение «portable», но данные не всегда лежат рядом с exe?**
По умолчанию используется надёжная пользовательская папка — установка может
находиться в read-only `/Applications` или `Program Files`:

- Windows: `%LOCALAPPDATA%\MONO Transcribe\`
- macOS: `~/Library/Application Support/MONO Transcribe/`
- Linux (для разработки): `~/.local/share/mono-transcribe/`

Чтобы хранить данные **рядом** с приложением на переносном диске, создайте
пустой файл `MONO.portable` возле exe или `.app`. При следующем запуске
появится папка `MONO-DATA`. Альтернативы: `MONO_PORTABLE=1` или `MONO_HOME=<path>`.
Требуется доступ к записи. Перенос самого Chromium/WebView профиля между ОС
не гарантируется: для этого используйте **Настройки → Экспорт библиотеки в папку**
и **Импорт из папки**. Эти функции требуют Chromium/Edge с File System Access API;
поддержка системных WebView не гарантирована.

## Подключение Groq (один раз, в самом приложении)

Записывать можно без ключа. Для расшифровки:

1. При первом запуске мастер настройки предложит подключить Groq: нажмите «Создать API-ключ»,
   скопируйте ключ из кабинета Groq и вставьте его в поле. MONO проверит ключ и сохранит его в
   защищённом хранилище системы (Windows DPAPI, связка ключей macOS).
2. Пропустили этот шаг — ключ можно подключить в **Настройки → Подключение Groq** или прямо при первой
   расшифровке: MONO откроет окно подключения и после него продолжит.

Редактировать файлы конфигурации не нужно. Для управляемых развёртываний (администратор, CI) ключ
по-прежнему можно передать через `GROQ_API_KEY` или `GROQ_API_KEY_FILE` — тогда в приложении он
показывается как «задан при запуске».

## Разработчикам: запуск из исходников

Требуются Python 3.11+, Node.js 20+, FFmpeg и FFprobe.

```bash
python launcher/mono_launcher.py --dev
python launcher/mono_launcher.py --dev --smoke
npm run check
npm test
PYTHONPATH=launcher python -m unittest discover -s launcher/tests -v
npm run test:e2e   # запись в реальном Chromium; нужен Playwright
```

Тесты, которым нужен закреплённый релизный тулчейн Windows (Python 3.14.8, MSVC,
собранный FFmpeg), пропускаются, пока не задано `MONO_RELEASE_TOOLCHAIN=1`. Тесты
системного хранилища ключей выполняются только на Windows и macOS.

`--dev` разрешает использовать системные runtime. Готовая сборка без него
**не подбирает случайные версии системного Node/FFmpeg**.

## Как собрать действительно автономный .exe/.app

Сборка производится **на целевой ОС** (не cross-compile).
Для Windows зафиксированы Python `3.14.8` (GIL, x64), Node `24.22.1` и инструменты сборки
в `launcher/requirements-build-windows*.lock` с хешами официальных PyPI-архивов.
В новом виртуальном окружении сначала установите bootstrap-lock командой
`python -m pip install --require-hashes -r launcher/requirements-build-windows-bootstrap.lock`,
затем основной lock с `--no-build-isolation --require-hashes`.
Не устанавливайте их поверх рабочего Python-профиля.

Для разработки на других ОС (нативная поставка macOS пока не завершена):

```bash
python -m pip install "pyinstaller>=6,<7" pywebview
python launcher/fetch_ffmpeg_release.py
```

Для Windows нужен .NET SDK `10.0.401` только на машине сборки. Нативный модуль
собирается со встроенным .NET `10.0.12`; пользователю устанавливать его не нужно.
Node загружается отдельным инструментом с закреплёнными SHA-256 архива,
исполняемого файла и лицензии. Октябрьское исправление безопасности:
[официальный выпуск 24.22.1](https://nodejs.org/en/blog/release/v24.22.1).
Выполните в PowerShell:

```powershell
python launcher/build_capture.py --output .build/capture-windows
$env:MONO_BUILD_CAPTURE_BUNDLE=(Resolve-Path .build/capture-windows/bundle).Path
python launcher/node_windows.py --output .build/node-windows
$env:MONO_BUILD_NODE=(Resolve-Path .build/node-windows/node.exe).Path
$gitRoot=Split-Path (Split-Path (Get-Command git.exe).Source)
python launcher/build_ffmpeg_windows.py --output .build/ffmpeg-windows --msys-bin "$gitRoot/usr/bin" --jobs 2
$env:MONO_BUILD_FFMPEG_BUNDLE=(Resolve-Path .build/ffmpeg-windows/bundle).Path
python -m pip install --no-build-isolation --require-hashes -r launcher/requirements-core-windows.lock
python launcher/fetch_msvc_windows.py --output .build/compiler-windows
python launcher/build_core.py --output .build/core-windows --compiler-input .build/compiler-windows --nuitka-archive .build/compiler-windows/archives/nuitka-4.3.1.tar.gz
python scripts/verify-compiled-core.py --bundle .build/core-windows/bundle --run-tests --report .build/core-windows/verification.json
$env:MONO_BUILD_CORE_BUNDLE=(Resolve-Path .build/core-windows/bundle).Path
python launcher/build_portable.py --stage .build/windows-stage --output .build/windows-dist
python scripts/verify-package.py '.build/windows-dist/MONO Transcribe' --execute --exercise-core --require-node-baseline --require-source-ffmpeg
```

Папки вывода должны быть новыми: сборщик сохраняет существующие сборки и staging.
Нативный вход проверяется по исходникам, SHA-256, архитектуре PE и лицензиям;
проверяется подпись NuGet-пакета .NET. `--execute` проверяет собственный собранный
EXE и перечисление устройств без запуска записи или основного окна приложения.
`--exercise-core` дополнительно создаёт отдельный временный архив с синтетическим
текстом и проверяет сохранение оригинала и правок после перезапуска worker-процесса.
`--require-node-baseline` обязателен для Windows-кандидата на выпуск: до запуска
дочерних процессов он сверяет точные байты исправленного Node и его лицензии.
Обычная проверка целостности без этого флага не подтверждает актуальность runtime.
Каждая команда должна завершиться успешно перед выполнением следующей; workflow
останавливается на первой ошибке. Для PowerShell-скрипта добавьте проверку
`if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }` после каждой внешней команды.

Windows FFmpeg собирается из точного исходного коммита по
`launcher/ffmpeg-source-windows.lock.json`. Нужен Git for Windows на машине
сборки; LLVM, NASM, GNU make и zlib загружаются в отдельную новую папку,
проверяются по SHA-256 до распаковки и исполнения и не устанавливаются в систему.
Для повторной автономной сборки можно передать `--cache` с пятью неизменёнными
архивами из предыдущей папки `archives`. Сборка сохраняет журналы и отказывается
перезаписывать существующие результаты. Включены аудиокодеки, аудиофильтры,
x86-оптимизации и zlib для сжатых заголовков MOV; сетевые протоколы, GPL/nonfree
и автоматическое подключение внешних библиотек выключены.
Семь DLL, полные исходники FFmpeg/zlib, рецепт, закреплённые входы, фактическая
конфигурация и оригинальные уведомления FFmpeg/LLVM/MinGW/zlib включаются в
ведомость целостности. `--require-source-ffmpeg` до запуска дочерних процессов
отклоняет прежний сторонний runtime; этот флаг обязателен в Windows CI.
Прежний `fetch_ffmpeg_windows.py` и его lock оставлены для проверки исторических
QA-пакетов: самообъявление LGPL той сторонней сборки не разрешает выявленное
расхождение с её зависимостью FFTW. Она не используется новым Windows workflow.
Сборщик отклоняет `--enable-nonfree`, запрет распространения, неизвестную лицензию
и неуспешную проверку `-L`. Это необходимая проверка, а не полное лицензионное
заключение: права на остальные компоненты, подпись издателя и проверка релиза
остаются самостоятельными требованиями. Старый `.ffmpeg-runtime` с nonfree
не подходит для распространяемой поставки и сохраняется только как прежний QA-вход.

`fetch_ffmpeg_release.py` загружает целевой FFmpeg/FFprobe из указанного GitHub
релиза, проверяет опубликованный SHA-256 и сохраняет provenance. Настоятельно
рекомендуется установить `MONO_FFMPEG_RELEASE_TAG=<проверенный тег>` для
воспроизводимой сборки; `latest` подходит только для разработки. Для сборки
используются `MONO_BUILD_FFMPEG` и `MONO_BUILD_FFPROBE` (полные пути) плюс
`node` из PATH. **В runtime конечного пользователя загрузки не происходят.**

`build_portable.py` формирует папку `MONO Transcribe/` (Windows), встраивает runtime,
нативный модуль, сверочную ведомость, лицензию Node.js и уведомления .NET.
Верификация также проверяет SQL-схему по фактическому пути frozen-пакета Python.
PyInstaller собирает Python-модули из подготовленного снимка; его целостность
проверяется до и после сборки. Обычная заморозка байткода сама по себе не защищает
исходный код от восстановления. SHA-256 ведомости встроен в EXE: случайно смешанные
компоненты или изменённая ведомость отклоняются. Это проверка целостности,
аутентичность издателя требует отдельной подписи релиза.

Для проверенного скомпилированного ядра Windows сборщик поддерживает отдельный
вход `MONO_BUILD_CORE_BUNDLE`: капсулу CPython 3.14.8 x64 с машинным модулем
`local_core`, ведомостью исходного снимка и уведомлениями среды компиляции.
Несовпадение исходников, архитектуры, хешей или комплекта файлов останавливает
сборку. В этом режиме исходники и Python-байткод локального ядра исключаются из
поставки; активный `.pyd` проверяется до импорта. Текущий QA-кандидат этого режима
проверен отдельно от обычной сборки. `compiler-msvc-windows.lock.json` фиксирует архивы
Nuitka, Microsoft VC и Windows SDK: загрузчик сверяет их до распаковки, сборщик повторно сверяет
каждый файл компилятора с проверенным архивом и весь исходный снимок до и после
компиляции. Сборка ограничена двумя задачами и использует отдельные кеши;
компилятор не входит в пользовательскую поставку. Эти же команды подключены к
Windows CI; удалённый запуск workflow ещё не проверен. Этот режим пока не покрывает код лаунчера,
JavaScript и нативного адаптера и не гарантирует невозможность реверс-инжиниринга.
Нативный адаптер захвата macOS ещё не реализован: сборщик отклоняет неполную
поставку macOS; она остаётся обязательным этапом проекта.
Python также включается PyInstaller. Для локальной проверки без PyInstaller:

```bash
python launcher/build_portable.py --prepare-only --stage .build/check-stage
```

GitHub Actions: `.github/workflows/portable-build.yml` собирает отдельные
артефакты для Windows x64, macOS ARM64, macOS Intel. Сам workflow в этой
сессии не запускался. Локальный Windows QA-кандидат проверяется отдельно;
поставка macOS остаётся незавершённой.

### Важные условия перед распространением

- **macOS:** подпись Developer ID + notarization, иначе возможны предупреждения
  Gatekeeper. Требуются реальные Apple Developer credentials владельца продукта.
- **Windows:** требуется настоящая подпись Authenticode владельца продукта;
  она не гарантирует отсутствие предупреждений SmartScreen для нового файла.
  [Microsoft описывает проверку репутации отдельно от подписи](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).
  Наличие WebView2/Edge на старых системах нельзя гарантировать.
- **FFmpeg:** проверьте лицензию конкретного бинарного билда (LGPL/GPL),
  выполните требования к распространению исходников/уведомлений.
- **Node:** распространяйте соответствующее уведомление и лицензии.
- **Системные разрешения:** микрофон/захват экрана всегда запрашиваются ОС
  или браузером; скрывать или обходить их нельзя.

Подпись, запуск на чистой целевой системе и тесты четырёхчасовой записи —
отдельные условия приёмки. Оценивать фактический запуск и системные предупреждения
нужно на конечной системе; одна подпись или успешная сборка этого не доказывают.

## Перенос с v0.3

В предыдущей версии библиотека могла находиться в **обычном браузерном профиле**.
Новый Chromium app window использует *изолированный профиль* и не читает
старую IndexedDB автоматически. Для переноса:

1. Запустите backend версии 0.4 обычной командой `npm start` или лаунчером.
2. Откройте **тот же браузер и профиль**, которым пользовались в v0.3, на
   `http://127.0.0.1:4173/`. В Настройках сделайте экспорт библиотеки.
3. Откройте отдельное окно MONO, импортируйте папку с `manifest.json`.
4. Проверьте количество записей, воспроизведение аудио и тексты до удаления
   исходного профиля.

Экспорт пишет данные потоково, а манифест последним. В случае сбоя папка без
манифеста считается неполной. Исходные данные при импорте **не перезаписываются**.

## Проверки и ограничения

Протокол текущей приёмки и отката: [`docs/qa/native-release.md`](docs/qa/native-release.md).
Исторический отчёт v0.4 сохранён в [`QA_REPORT_0.4.0.md`](QA_REPORT_0.4.0.md);
он не описывает все последующие изменения.

Локальные проверки включают реальные браузерные сценарии по HTTP, запуск
собранного Windows EXE без GUI, встроенный worker, целостность и отказ при
повреждении компонентов. Импортированное тестовое аудио и исходный/исправленный
текст проверяются после перезапуска. Перечисление аудиоустройств не подтверждает
физическую запись; stub-провайдер не подтверждает качество расшифровки.

**Открытые ворота выпуска:** физический захват микрофона/системы/обоих источников,
обычное окно и повторный запуск, чистая Windows без системных runtime,
четырёхчасовая запись и восстановление при аппаратных сбоях, реальный Groq/WER,
полные условия распространения зависимостей, подпись и независимый итоговый
обзор. macOS требует отдельной реализации и целевой проверки. Текущие локальные
QA-кандидаты не обозначены как production-релиз.

Для удалённого размещения (Docker/Caddy) остаётся отдельный
[`ops/DEPLOY.md`](ops/DEPLOY.md); приложение из этого README предназначено
именно для **локального self-hosted режима**, без экспонирования порта наружу.
