# MONO: спецификация доработки интерфейса и локального ядра

Дата: 16 октября 2026. Статус: ПРОЕКТ ДЛЯ СОГЛАСОВАНИЯ, реализация не начата.

## 1. Результат и границы

Пользователь открывает портативное приложение двойным кликом, один раз выбирает место для архива и подключает распознавание, после чего записывает микрофон, звук компьютера или оба источника. Записи, исходные расшифровки и правки сохраняются в назначенной папке независимо от профиля браузера. До отправки на распознавание можно сравнить исходное и подготовленное аудио. Интерфейс сохраняет монохромный характер MONO, становится спокойнее, последовательнее и удобнее.

Обязательные платформы подтверждены пользователем: Windows и macOS. Предлагаемая матрица: Windows 10 22H2 / Windows 11 x64; macOS 14.2+ Apple Silicon и Intel. Минимум macOS — предложение в этом проекте ТЗ, а не уже согласованное ограничение. Сборка и приемка проводятся отдельно на каждой архитектуре. Linux не входит в этот выпуск; существующий удаленный proxy-режим сохраняет свой контракт и не получает возможности управления локальным компьютером.

«Премиальность» проверяется по целостности компонентов, поведению, визуальному обзору и измерениям. Субъективное сравнение с Apple само по себе не является доказательством приемки.

## 2. Установленные факты об исходной версии

- Версия package.json: 0.4.0. Интерфейс: HTML/CSS и JavaScript ES modules; HTTP-сервер: Node; supervisor и упаковка: Python/PyInstaller.
- Git-репозиторий в рабочей папке отсутствует. До правок требуется контрольный снимок исходников с SHA-256; существующий dist не является источником истины.
- public/db.js хранит метаданные, импортированные файлы и блоки записи в IndexedDB.
- public/app.js использует MediaRecorder и getDisplayMedia; выбранный браузером экран может не отдавать звук.
- server.mjs читает ключ Groq при старте. Пользовательского ввода и безопасного сохранения ключа через интерфейс сейчас нет.
- Три профиля FFmpeg заданы строками в encodeSegment; прослушивания результата обработки до расшифровки нет. Текущий фильтр и нормализация применяются отдельно к сегментам.
- checkHealth и wire обращаются к удаляемым sidebar-status-title, sidebar-status-caption, network-label, open-settings. Удаление только разметки нарушит работу JavaScript.
- Присутствует Service Worker. Обновление UI должно исключить смесь старых и новых модулей.
- Свежая базовая проверка: npm run check — exit 0; node --test tests/core.test.mjs tests/backup.test.mjs — 10 PASS, exit 0. Полный набор тестов, актуальная нативная сборка, живой захват и Groq в этой сессии еще не проверялись.

## 3. Выбранное направление и альтернативы

Рекомендация: сохранить frontend и Node HTTP, добавить локальное ядро с файловым архивом и нативные модули захвата. Python уже входит в поставку; SQLite доступна через его стандартную библиотеку. Приватный worker работает с SQLite и файлами, а Node обращается к нему через протокол запросов по stdin/stdout. В packaged-режиме используется отдельный режим того же поставляемого executable; для macOS захват выполняет встроенный Swift helper, для Windows — модуль WASAPI. Жизненный цикл контролирует supervisor. Это предложение архитектуры для согласования, не утверждение о наличии работающих модулей.

Альтернатива 1: сохранить браузерное ядро и сделать File System Access основным хранилищем. Меньше изменений, но доступность API в macOS WebView и захват произвольного системного звука не обеспечивают требуемый результат.

Альтернатива 2: полностью перейти на новый desktop framework. Можно унифицировать shell, но потребуется переписать и заново проверить больше существующего кода без прямой пользы для архива и транскрибации. Оснований для такого масштаба сейчас нет.

Границы модулей: UI components/tokens; onboarding/help; library client; LibraryService; CaptureService с платформенными adapters; AudioPreparation; GroqAdapter; supervisor/packaging. Единые схемы ошибок, состояний, возможностей и настроек. Разбивка app.js и server.mjs выполняется только по затронутым обязанностям.

R-002: убрать белую полосу выбранной навигационной кнопки, включая nav-active-indicator и CSS pseudo-elements, создающие тот же эффект. Выбор обозначается единым фоном, контуром и текстом; aria-current отражает активный раздел.

Микрорасстояния 1/2 px допустимы только как именованные токены. Высоты контролов 40/44 px, крупного действия 48 px; исключения для scroll arrows и плотных player-контролов описываются в компоненте. Токены размеров иконок, радиусов, границ, теней, слоев, типографики и движения. Адаптив меняет семантические значения, а не создает произвольные локальные отступы.

R-004: централизовать letter-spacing, line-height, tabular-nums, расстояния иконка–текст и знак–число. Читабельная кириллица, корректные многоточия и переносы; узкие окна, длинные названия и 200% масштаб не ломают расположение. Единые видимые состояния default/hover/pressed/focus/disabled/busy/error.

R-005: все списки выбора внутри приложения используют один кастомный Select/Combobox с popup в верхнем слое, доступным именем и ролями, клавиатурой, поиском по вводу и возвратом фокуса. Enter/Space, стрелки, Home/End, Escape и Tab работают предсказуемо; disabled options не выбираются. Popup учитывает границы окна, внутреннюю прокрутку, zoom, закрытие снаружи и смену маршрута. Один источник состояния, без двух рассинхронизированных значений native/custom. На системные диалоги ОС этот компонент не распространяется.

R-006: единые Checkbox, Radio, Switch, Range, NumberInput и поле пароля. Нативная семантика input сохраняется, визуальная часть кастомная. Проверить checked/unchecked/indeterminate, radio group keyboard, ошибку, отключение, клавиатуру, forced-colors и focus. Браузерные number spin buttons и player range не остаются случайным системным оформлением.

R-007: все области прокрутки приложения получают единый ScrollArea с собственными дорожками, бегунками и стрелками обоих направлений. Включены основной экран, sidebar, dialog, select popup, transcript и длинные редактируемые поля. Полоса резервирует место и не перекрывает содержимое; при отсутствии overflow элементы не занимают ложную область. Drag, track click, удержание стрелки, wheel, touch, PageUp/Down, Home/End, горизонтальная прокрутка и вложенные области работают. Размер бегунка зависит от viewport/content и имеет минимум 24 px. Стрелки отключаются у края; нет дублирования со штатной полосой. Scrollbar получает доступное имя, orientation/value и keyboard behavior. Наблюдатели и обработчики очищаются при удалении компонента. Системные окна выбора файлов и разрешений сохраняют оформление ОС.

R-008: иконка «Настройки» — зубчатое колесо с центральным отверстием в существующем SVG-стиле. Солнце/луна используются только для темы.

R-009: motion tokens: обратная связь 100–140 ms; popup/fade 140–180 ms; dialog/sidebar/route 180–240 ms. Общая кривая easing; transform/opacity для основных переходов. Быстрые повторные действия прерывают/перенаправляют переход к актуальному состоянию без очереди и блокирования ввода. При reduced-motion остаются мгновенные состояния и необходимая индикация; декоративные бесконечные анимации не добавляются. Во время записи не возникает постоянного layout/repaint всей страницы. Цель в измеряемом тестовом окружении — отсутствие вызванных анимацией long tasks >50 ms и отсутствие анимационно вызванных layout shifts.

R-010: glass применяется к sidebar, topbar, popup, dialog и player там, где подложка действительно создает глубину. Контентные карточки спокойнее; текст остается контрастным в обеих темах. Без вложенных тяжелых blur-слоев и без потери читаемости при fallback без backdrop-filter.

Обычный закрепленный desktop-sidebar не размывает страницу. Resize через breakpoint и переход по навигации полностью очищают overlay-состояние.

R-012: приемка каждого экрана в обеих темах, на ширинах 390/768/1024/1440 CSS px и при 200% zoom. Ни горизонтального вылезания страницы, ни перекрытия кнопок, текста, popup, sticky player и scrollbar. Оценить пустые/заполненные/ошибочные/загружающиеся состояния, видимость фокуса и клавиатуру. Одинаковые элементы сравниваются по вычисленным токенам, исключения перечисляются.

## 6. Первый запуск, Groq и подсказки

R-013: короткая возобновляемая настройка из трех шагов. 1) «Где хранить записи» — готовое локальное расположение и «Выбрать папку». 2) «Подключить расшифровку» — одна короткая фраза, password-поле, «Получить ключ Groq», «Подключить», «Позже». 3) «Проверить звук» — источник и короткий тест с реальными индикаторами и прослушиванием. Лишние детали раскрываются по запросу; никаких ручных файлов конфигурации и обязательного перезапуска. Микрофон запрашивается только после соответствующего действия. Повторный запуск использует завершенные шаги; изменение настроек доступно всегда.

Пример текста шага 2: «Groq превращает аудио в текст. Создайте ключ в своем аккаунте и вставьте его сюда». Ниже — «Записывать и сохранять можно без ключа». Раскрытие «Ключ и оплата»: 3 шага создания ключа; ссылка на официальный раздел оплаты; пояснение, что платный тариф подключается в аккаунте при необходимости. Не требовать оплату до проверки доступного тарифа и не обещать способы оплаты, доступность в стране или фиксированные лимиты без подтверждения провайдера.

R-014: ключ вводится только пользователем, передается локальному ядру один раз, проверяется запросом к Groq без отправки аудио. Успешная проверка ключа не выдается за подтверждение оплаты/доступности конкретной аудиомодели. Сохраняется через DPAPI CurrentUser в Windows / Keychain в macOS. Не хранится в localStorage/IndexedDB, исходниках, логах, архиве библиотеки, backup, URL или диагностических ответах; UI читает только configured/verified/error и маску. Замена и удаление ключа доступны без перезапуска. Keychain denied/locked не приводит к незаметному plaintext fallback. Перенос папки на другую ОС требует повторного подключения ключа.

R-015: классифицировать unauthorized, rate limit, quota/billing, network, timeout, provider error; для каждой ошибки показать одно понятное действие. Проверка не запускается бесконечно и не дублируется двойным кликом. При отсутствии ключа запись/импорт/редактор доступны; начало транскрибации ведет к короткой настройке с возвратом к выбранной записи.

R-016: контекстные подсказки вместо постоянного тура. Перед митингом — выбрать «Микрофон + компьютер», использовать наушники при риске эха, проверить сигнал. При тишине/перегрузке — ненавязчивое конкретное действие. После записи — проверить фрагмент, при необходимости подготовить звук и расшифровать. При повторном использовании подсказки не появляются заново без причины; есть «Не показывать» для обучающих советов и раздел помощи. Критические ошибки сохранения не скрываются этой настройкой.

R-017: отправка аудио в Groq остается явным действием с подтверждением назначения, выбранного варианта и оценочной стоимости. Ключевая информация появляется именно перед отправкой; данные не отправляются при welcome, тесте звука, preview обработки или выборе папки. Тариф и валюта имеют источник/дату проверки; оценка не называется фактическим счетом. Повтор платного задания требует понятного подтверждения, уже подтвержденные серверные результаты не оплачиваются повторно из-за восстановления.

## 7. Файловый архив

R-018: основное хранилище — назначенная пользователем папка MONO Library. Предложение по умолчанию: MONO Library внутри Documents; системные настройки/ключ отдельно в user-data/Keychain. Аудио лежит отдельными файлами; SQLite содержит схему, метаданные, состояния, связи, поисковый индекс и ссылки. Исходная расшифровка и правки сохраняются раздельно, есть экспортируемые версионированные JSON. Индекс можно восстановить из файлов и manifest/journal; секреты не копируются в архив. IndexedDB остается только источником миграции и необязательным восстанавливаемым UI-кэшем.

R-019: записи пишутся потоком короткими независимо восстанавливаемыми сегментами с последовательностью, длительностью, checksum и журналом фиксации. «Сохранено» означает подтвержденную устойчивую запись, а не наличие в RAM или принятие HTTP-запроса. Цель: фиксированный сегмент 2 s; неожиданное завершение не должно терять подтвержденные сегменты; неподтвержденный хвост показывается честно. Итоговое аудио собирается потоково с проверкой целостности. Закрытие окна/падение/сон/перезапуск восстанавливают доступные данные с явным статусом interrupted. Отсутствующие куски не склеиваются как непрерывная запись без отметки разрыва.

R-020: атомарные изменения метаданных, транзакции SQLite, flush и recovery журнал, один writer на библиотеку. Не читать/собирать многочасовое аудио целиком в JS RAM. HTTP Range для player; постраничные метаданные/транскрипт. Контроль свободного места до записи и во время нее; read-only/full-disk/отключение накопителя не показывают фиктивный успех и не перезаписывают оригиналы. SQLite и journal на обычной локальной файловой системе; сетевые папки не принимаются как надежная база без специальной проверки. Синхронизируемые папки распознаются, если возможно; база не открывается конкурентно разными копиями MONO.

R-021: миграция существующей IndexedDB — копирование без удаления, журнал с контрольными суммами, сравнение количества записей, длительностей/аудио, исходных текстов и правок. Повтор/перезапуск миграции не создают дубликаты. Только подтвержденные записи считаются перенесенными. Источник сохраняется; очистка браузерного архива — отдельное явно подтвержденное действие. Если старый профиль недоступен новому окну, пользователь открывает прежний профиль для экспорта; не заявлять автоматический доступ к чужому browser profile.

R-022: изменение пути архива в настройках. Без активной записи/изменяющих заданий: проверить назначение, скопировать, проверить manifest/checksums, атомарно переключить указатель; исходная библиотека остается. Недоступная папка приводит к предложению подключить/выбрать существующую библиотеку, а не к незаметному созданию пустой. Import/export сохраняют исходное аудио, текст, правки и историю обработки. Коллизии ID/неполные копии/неподдерживаемая версия/повреждение выявляются до успешного подтверждения. Удаление записи идет через корзину приложения с восстановлением; окончательная очистка подтверждается отдельно.

## 8. Захват звука

R-023: единый CaptureService: список возможностей и устройств, проверка доступа, test/start/pause/resume/stop/status. Состояния idle/requesting/ready/recording/paused/stopping/interrupted/error; один активный сеанс. Реальное сохранение выполняется локальным ядром, независимо от частоты перерисовки страницы. UI не отдает helper произвольные команды, исполняемые пути или пути файлов.

R-024: Windows — WASAPI loopback выбранного output endpoint и отдельный микрофонный input. macOS — Core Audio taps для системного аудио и Core Audio/AVFoundation для микрофона. Не требовать пользователю установить Stereo Mix или виртуальный аудиодрайвер. Поддержать системный default и явный выбор устройства. «Любой источник» означает обычное воспроизводимое системой аудио приложений на выбранном выходе, включая браузер, плеер и митинг. Несколько output-устройств — явный выбор, не обещание захвата всех физических маршрутов одновременно. Защищенное DRM, эксклюзивные аппаратные маршруты и системные ограничения не обходятся; UI сообщает неподдерживаемую возможность вместо пустой успешной записи. Выбор отдельного процесса не входит в этот выпуск.

R-025: микрофон, компьютер и совмещенный режим. Для совместного режима сохранять отдельные исходные дорожки и производный mix. Общая монотонная шкала времени, компенсация drift/resampling, сохранение тишины и явных разрывов; никаких накопленных сдвигов и удаления пауз. Микширование с headroom, отдельными уровнями и защитой от clipping. MONO не включает live playback входящего микрофона по умолчанию. Для A/B прослушивания запись останавливается, чтобы player не попал обратно в loopback.

R-026: тест сигнала обоих источников, короткая локальная проба и playback до митинга. Отказ в разрешении, отзыв доступа, занятое/удаленное устройство, смена default, Bluetooth/наушники, sleep/wake и обрыв helper имеют конкретное состояние и безопасное завершение/восстановление. Нельзя незаметно подменять отключенный микрофон другим и продолжать запись. Не требовать разрешения камеры для аудио-only функций. Системные запросы и инструкции соответствуют реальной ОС; разрешения не обходятся и не обещаются «один раз навсегда».

## 9. Подготовка аудио и сравнение

R-027: сначала локальный анализ: длительность, каналы, формат, sample/true peak, clipping, интегральная громкость и пригодность измерения, оценка тишины/шума с отметкой эвристического характера. Для короткого/тихого материала не выдумывать LUFS/noise score. Наличие шума не доказывается одним низким уровнем громкости.

R-028: режимы «Оригинал», «Бережно», «Выровнять голос», «Убрать ровный шум». По умолчанию — осторожная подготовка формата; при неопределенности не применять агрессивное шумоподавление. Рекомендация объясняется наблюдением, пользователь может изменить выбор. Нормализация с анализом целой записи и согласованным gain; обработка общей дорожки до сегментации для Groq, чтобы границы chunk не меняли громкость/шумоподавление. Пресеты, фильтры и версии pipeline централизованы и совпадают между preview и полной обработкой. Оригинал никогда не заменяется.

R-029: единый player «Оригинал / После обработки»: play/pause/seek/скорость/громкость, одна временная позиция, только один звучащий вариант. Переключение готовых вариантов сохраняет позицию с точностью до 100 ms; нет щелчка, скачка уровня из-за ошибки переключателя или второго одновременно играющего player. Режим «Сравнить при одинаковой громкости» включен по умолчанию для честной оценки; возможность услышать фактический gain явно доступна. После выбора профиля локально готовится выбранный короткий фрагмент с контекстом фильтра; индикатор подготовки реален. «В реальном времени» здесь — непосредственное A/B прослушивание готовых вариантов, а не обещание мгновенной обработки многочасового файла. Seek в неготовую часть явно запускает подготовку; быстрые изменения отменяют устаревшие операции.

R-030: перед транскрибацией показать выбранный вариант, профиль и возможность прослушать. AudioPreparation работает локально и без Groq. Тишина не вырезается, скорость не меняется, длительность остается в пределах одного frame целевого sample rate после учета codec padding, временные метки отображаются в шкале оригинала. Проверить импульсы, паузы, границы фрагментов, stereo/mono, разные sample rates и многочасовой материал. Preview согласуется с тем же участком полной производной версии с документированной численной/акустической погрешностью.

R-031: доказать полезность обработки на разрешенном речевом корпусе: чистая речь, постоянный шум, тихая речь, clipping, стерео с противофазой и два говорящих. Минимум 3 разных речевых фрагмента по 30–60 s на каждую категорию; исходники и человеческие эталонные тексты фиксируются hash до изменения фильтров. Нормализация текста для WER одинакова у всех вариантов и фиксируется до сравнения. На чистой речи авто-режим не должен увеличивать агрегированный WER более чем на 1 процентный пункт; на шумной речи профиль, рекомендованный автоматически, должен снижать агрегированный WER относительно оригинала, иначе такую рекомендацию и утверждение об улучшении не выпускать. Сохранить замеры peak/LUFS/длительности, прослушивание артефактов и WER при реальной транскрибации. Синусоидальная fixture проверяет DSP и шкалу времени, но не качество речи. Если реальный Groq/корпус недоступен, качество распознавания остается NOT_RUN, а не объявляется улучшенным. Тестовые разговоры пользователя не отправляются в облако без его явного действия.

R-032: очередь подготовки отдельно от облачной очереди. Progress/cancel/retry показывают реальные этапы; отмененный/устаревший результат не заменяет новый. Cache key включает hash оригинала, дорожки, параметры и версию pipeline. Не использовать старый FLAC только потому, что файл существует. Ограничить диск/параллелизм/CPU и чистить только производные временные файлы, не библиотеку и не оригиналы.

## 10. Защита локального ядра

R-033: только loopback; проверка Host/Origin, session capability для локальных операций и CSRF-защита изменяющих запросов. Bootstrap-секрет не попадает в URL/логи/кэш. Защита распространяется на HTTP и event/WebSocket каналы, если они добавляются. Случайный идентификатор instance не считается полноценной авторизацией. В proxy-режиме отсутствуют endpoints выбора папки, настройки локальных ключей и нативного захвата.

R-034: все операции архива используют IDs и разрешенный корень, проверяют traversal, reparse/symlink, неожиданные расширения и лимиты; нет произвольного чтения/записи файлов через HTTP. Нативный folder picker — отдельная операция с участием пользователя, не произвольный путь от страницы. Запуск helper/FFmpeg только с фиксированным executable и массивом аргументов без shell. Недоверенные имена/расшифровки отображаются как текст. Не логировать Authorization, ключи, аудио, transcript и полные приватные пути. Разделить пользовательский архив, config и временные файлы.

## 11. Проверка, упаковка и критерии завершения

R-035: сохранить действующие контракты сегментации, overlap, русского prompt, retry/idempotency, recovery, ack cleanup, ограничений upload, backup/import и proxy. Service Worker получает согласованное обновление модулей; чувствительные endpoints не кэшируются. Добавить RED/GREEN для новых требований и независимые негативные проверки оракула до изменения логики.

R-036: реальные portable-пакеты Windows x64, macOS ARM64 и macOS Intel со встроенными runtime, нативными helpers, licenses, pinned versions и manifest SHA-256. Проверки сборки сами по себе не закрывают запуск. На каждой платформе: чистое окружение без системных Node/Python/FFmpeg, двойной запуск, первый запуск, разрешения, отказ в доступе, реальная микрофонная/системная/смешанная запись, архив, preview, перезапуск, длительная запись и аварийное восстановление. Публикация, платные ресурсы и использование учетных данных требуют отдельного поручения. Для подписанной/нотаризованной macOS поставки нужны учетные данные владельца; отсутствие подписи не маскировать обходом Gatekeeper. На текущем Windows-компьютере macOS runtime-приемка невозможна; она остается отдельным обязательным gate, а не заменяется статическим анализом Swift.

## 12. Порядок поставки и точка согласования

Этапы для последующего подробного плана: (1) контрольный снимок/полный baseline и UI-компоненты; (2) защищенный локальный bridge и файловый архив с миграцией; (3) нативный захват Windows/macOS; (4) onboarding/key storage/help; (5) AudioPreparation и A/B; (6) общая регрессия, adversarial review, нативные пакеты и приемка. Каждый этап имеет собственный измеримый gate; дизайн не считается принятым вместо проверки механизмов.

Сейчас требуется согласовать именно это ТЗ, включая рекомендованную архитектуру, предложенный минимум macOS 14.2+ и конкретную трактовку A/B. Затем создается отдельный подробный implementation plan с командами, файлами, оракулами, rollback и способом исполнения. Изменение продуктового кода начинается после согласования плана. Документ не фиксирует неподтвержденное разрешение на публикацию, оплату, удаление существующих данных или изменение системных security-настроек.
